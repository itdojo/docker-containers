# ntopng inline-bridge sensor — working notes

## Decisions

- 2026-08-19: **The int sensor moved off the Gateworks GW7400 to an ODROID-H4 (`ntopng-int`), and the DSA problem goes away with it.** Board reports `ODROID-H4` in DMI but carries an **Intel i3-N305, 8 cores, 30 GiB usable RAM, x86_64**, Ubuntu 26.04 LTS, systemd 259. Four NICs, all independent, no switch chip: `enp1s0` + `enp2s0` (Intel `igc`, on-board 2.5GbE) and `enx00e04c9a1b47` + `enx00e04c99a6ba` (Realtek `r8152`, USB). Every frame between members transits the CPU, which is the property the GW7400 could not provide.
- 2026-08-19: **x86_64, so the arm64 path never fires here.** `ensure_arch_image` returns immediately, `NTOPNG_IMAGE` stays unset, and compose falls back to `ntop/ntopng:latest`. The Dockerfile.arm64 work stays valid for a future SBC; it is simply not used on this host.
- 2026-08-19: **Sizing needs no change: 30 GiB against a `.env` written for 32 GB.** `warn_on_sizing` passes (16384 MB of ceilings + 768 MB headroom against 30720 MB). `MAX_FLOWS=1500000` / `MAX_HOSTS=400000` are absurd for a ~20-device lab but they are caps rather than reservations, and there is RAM to spare, so they are left alone.
- 2026-08-19: **`bridge0` grows from 2 members to 4, and STP is turned ON — reversing the shipped int design.** A two-port inline tap has no loop to break and should keep `stp: false`; a four-port bridge in a room where students patch cables will eventually have two of its ports landed on one segment, and without STP that is a broadcast storm across the whole lab. Timers are `forward-delay: 4`, `hello-time: 1`, `max-age: 6` — roughly 8s to forwarding instead of the default ~30s. `max-age` is pinned because 802.1D wants `max-age <= 2 x (forward-delay - 1)` = 6; the kernel accepts the default 20 against `forward-delay 4` without complaint (verified on a throwaway bridge), so the inconsistency is silent and would only bite if a real STP peer appeared.

- 2026-08-18: **arm64 support is an image-source problem, solved behind one variable: `NTOPNG_IMAGE`.** `compose.yaml` now reads `image: ${NTOPNG_IMAGE:-ntop/ntopng:latest}` and knows nothing else about architecture. Unset means amd64 and the upstream image; on arm64 `host-setup.sh` builds `Dockerfile.arm64` and writes the tag into `.env`. Chosen over putting a `build:` block in compose because the existing constraint says `compose.yaml` must stay identical at both positions — and an arch branch in that file is the same kind of branch, one step from being the argument for two packages again.
- 2026-08-18: **Arch is detected with `uname -m` in `check_prerequisites`, never inferred from `POSITION`.** Which side of the firewall a sensor sits on says nothing about its CPU. An unknown arch is a hard exit, since ntop ships an amd64 image and arm64 packages and nothing else.
- 2026-08-18: **The arm64 image is built on the sensor, not cross-built and pushed.** Keeps the repo self-sufficient — no registry credentials, no publish step between cloning and standing up a sensor. Costs a few minutes on first run; reruns hit the layer cache. `ensure_arch_image` refuses to build without a default route and, under `POSITION=ext`, prints the `docker save | ssh` side-load path instead, mirroring how `ensure_images` already handles a routeless host.
- 2026-08-18: **`Dockerfile.arm64` installs `apt-ntop.deb` rather than hand-writing a sources.list.** ntopng Depends on `ntopng-data (= 6.7.260805)` and `ndpi (= 5.1.0-5955)` at exact versions, both of which exist only in ntop's repo, so installing the single `.deb` cannot resolve. The postinst also picks the arm64 path off `uname -m` itself. Base is `debian:bookworm-slim` because the package's Depends names bookworm library versions (`libldap-2.5-0`, `libhiredis0.14`, `libsnmp40`).
- 2026-08-18: **`host-setup.sh` gained `warn_on_sizing`, which checks `NTOPNG_MEM + REDIS_MEM` against `MemTotal` and prompts (default N) when they do not fit.** Warns rather than refuses: the ceilings are a blast radius, not a reservation, and the right headroom depends on what else runs on the box. This is the check that would have caught the 32 GB assumption before a night of OOM kills.

- 2026-08-14: **`lan-monitor/` and `outside-fw/` collapsed into one package at `ntopng/`.** The LAN version was to be a second container design; it isn't one. The delta is four knobs — which netplan, whether the networkd drop-in carries `MulticastDNS`, whether a wildcard `WEB_BIND` is a hard error or a warning, and which way `LOCAL_NETS` is sanity-checked. `compose.yaml`, both sysctl files, `netprep`, the redis tuning, the ring buffers and ~90% of `host-setup.sh` are identical, so two packages would have meant maintaining two copies of a 1100-line script to vary those four. `POSITION=ext|int` in `.env` instead. Also matches the repo convention: every sibling (`mediamtx`, `pihole-dnscrypt`, `hostapd`) is one top-level dir = one deployable stack.
- 2026-08-14: **`int` gets its address by DHCP on `bridge0`, not a static.** User's call. Consequence: no stable address to pin, so `WEB_BIND=0.0.0.0` is the documented default for that position, and access is by `<hostname>.local` or a DHCP reservation.
- 2026-08-14: Netplan stays two hand-editable files in `etc/netplan/`, selected by `POSITION`, rather than being generated from `.env` by the script. Generating would have killed the `BRIDGE_PORTS`-must-match-the-yaml duplication (still an open wart), but the user wanted the file to stay a file. Both install to the position-neutral `/etc/netplan/10-ntopng-bridge.yaml`, so moving a sensor between positions replaces the stanza instead of stacking a second one.
- 2026-08-14: The wildcard `WEB_BIND` rule is asymmetric by consequence, not by taste. `ext` hard-fails (a wildcard there publishes an admin/admin UI to the internet); `int` warns, prompts, and proceeds. Compose's `:-127.0.0.1` fallback stays loopback for *both* — an unreachable int sensor is a nuisance, a reachable ext one is an incident.
- 2026-08-14: `MulticastDNS=yes` rides in the existing `promisc.conf` drop-in for `int` only, reusing the machinery already there for `Promiscuous=yes` (netplan has no key for either). Not set for `ext`: answering mDNS means announcing yourself on the monitored segment, which is the opposite of what an inline sensor on the dirty side should do.
- 2026-08-14: `dhcp-identifier: mac` on the int bridge. systemd-networkd defaults to an RFC 4361 DUID-derived client identifier, which DHCP servers matching reservations on the hardware address do not recognise — the classic "my reservation is ignored on Ubuntu" symptom. The user said they may make a reservation, so this is load-bearing for that.
- 2026-08-14: **`verify_bridge_address` waits up to `DHCP_WAIT=45s` for the int lease rather than just checking for it.** The wait is load-bearing for a *later* step: `apply_network` does not block on the lease (`bridge0` is `optional: true`), and only a few fast `ip`/`sysctl`/`ethtool` calls separate it from `ensure_images` calling `have_default_route`. Sampling mid-negotiation told an int host with a working DHCP server that it had no route and must side-load its images.
- 2026-08-14: `ensure_images`' no-route error is position-aware. Under `ext` a missing route is the design; under `int` it is a fault, and the fix is the lease, not `docker save`.
- 2026-08-14: SPAN / mirror-port mode considered and **not** built. It is a third design rather than a third value of `POSITION`: no bridge, no forwarding, and `verify_host`'s promiscuous check, `netprep` and the whole `br_netfilter` story all change. Documented as unsupported in the README rather than half-built.
- 2026-08-14: **ClickHouse removed entirely.** Superseded an earlier same-day decision to promote it from a compose profile to a standard service; that call assumed the export could work at all. It cannot: `--dump-flows=clickhouse` (and `clickhouse-cluster`, `clickhouse-cloud`, `kafka`) is Enterprise M/L/XL/XXL, and with no `/etc/ntopng.license` ntopng logs `[LICENSE] ntopng will start in community mode` and ignores the flag. Keeping it would reserve 8 GB and a service to receive nothing. The 8 GB went to ntopng instead (`NTOPNG_MEM` 8g → 12g, `MAX_FLOWS` 1000000 → 1500000, `MAX_HOSTS` 250000 → 400000, conservative bumps to be tuned from a week of traffic). Community mode keeps live flows, host table, alerting and the UI; only historical storage is lost.
- 2026-08-14: Image is `ntop/ntopng:latest`. `ntop/ntopng:stable` — what the package originally referenced — **does not exist**; only `latest` is published for both `ntop/ntopng` and `ntop/ntopng.dev`. `.dev:latest` is the development build and ships no `/usr/bin/clickhouse-client`, which produced a *different* warning (`not available (ClickHouse client not found)`) than the licence one, and masked the real cause for a while.
- 2026-08-14: ntopng's entrypoint is overridden to `["ntopng"]`, bypassing the image's `/run.sh` (`/etc/init.d/redis-server start; ntopng "$@" $NTOP_CONFIG`). The bundled redis is redundant against our tuned one, would race the published `127.0.0.1:6379` under `network_mode: host`, and its startup chown of `/run/redis` needs `CAP_CHOWN` — the source of the `chown: Operation not permitted` lines.
- 2026-08-14: `WEB_BIND` and `WEB_PORT` carry `:-` defaults in `compose.yaml` (`127.0.0.1`, `3000`). Every other variable already had one; these two did not, and they were the two where the failure mode was exposure rather than a bad default.
- 2026-08-14: `host-setup.sh` restyled to the qol house style (`~/projects/qol/script-design.md`). Embeds the theme block verbatim rather than sourcing `base_functions.sh` — same call `mediamtx-users.sh` made, for a stronger reason: this host has no default route, so the auto-download-from-GitHub fallback in `kernel_update.sh` would fail exactly when needed. Region copied is lines 44–371; keep it byte-identical.
- 2026-08-14: Script uses `set -eo pipefail`, not `-euo`. House style; the theme block is written against it and guards its own optional vars with `${VAR:-}`.
- 2026-08-14: Script refuses to run as root and takes `sudo` per step, per house style, replacing the old `check_root`-and-exit gate.
- 2026-08-14: First run creates `.env` and stops rather than continuing with placeholders. Bringing the stack up with an unedited `.env` is the failure this package most needed to prevent.
- 2026-08-14: `host/ntopng-tap.service` added and enabled by the script. Docker's restart policy does not honour `depends_on`, so a reboot brought ntopng back without re-running `netprep`.
- 2026-08-14: `REDIS_MAXMEM` 3gb → 2gb rather than raising `REDIS_MEM` 4g → 6g, to keep the unallocated headroom intact.
- 2026-08-14: `host-setup.sh` reads the image list from `docker compose config --images` instead of hardcoding it. The hardcoded copy went stale within the hour, when the ntopng image was repinned to `ntop/ntopng.dev:latest`. Same reasoning applied to the README's pre-pull instructions.

## Gotchas

- 2026-08-19: **`bridge0` does NOT inherit the lowest member MAC on this host — the folklore answer is wrong on modern systemd.** `/usr/lib/systemd/network/99-default.link` ships `MACAddressPolicy=persistent` matching `OriginalName=*`, which matches bridge devices, so `bridge0` takes a locally-administered MAC derived deterministically from machine-id + device NAME. On `ntopng-int` that is **`b2:65:07:e1:40:6e`**, verified stable across repeated create/delete. Consequences: the host will NOT keep the address `enp1s0` holds today (172.16.44.165), the new MAC is stable enough to reserve against, and it can be read before committing to anything via `ip link add bridge0 type bridge` on a throwaway. Pinning `macaddress:` on the bridge stanza is the escape hatch if the existing address must be preserved.
- 2026-08-19: **Ubuntu 26.04 + subiquity's `00-installer-config.yaml` does NOT conflict with the bridge netplan — verified by rendering, not assumed.** The installer file declares `enp1s0: dhcp4: true` plus `match`/`set-name`, which looks like a fight with a file that makes `enp1s0` an addressless bridge member. Netplan merges per key and the higher-numbered `10-ntopng-bridge.yaml` wins: rendering both together yields `enp1s0.network` with `Bridge=bridge0` and no DHCP, the only residue being a harmless `PermanentMACAddress=` in the `[Match]`. So the installer config needs no retirement, and `host-setup.sh` needs no new code for it. Test it on any new host with `netplan generate --root-dir /tmp/x`, which renders without touching the live config.
- 2026-08-19: **The repo targets Ubuntu 24.04; `ntopng-int` runs 26.04 LTS with netplan 1.2 and systemd 259.** No incompatibility found — `MIN_SYSTEMD=249` passes, `renderer: networkd` is active, NetworkManager is inactive, and the bridge renders correctly including `STP=true` / `ForwardDelaySec=4` / `MaxAgeSec=6` / `ClientIdentifier=mac`.
- 2026-08-19: **Pre-cutover state, captured passively 2026-08-19: the three downstream ports are cabled and carrying link, but isolated — they are not yet joined to the lab.** `enp1s0` is the live lab segment (172.16.44.0/24, gateway .1, host lease .165). `enx00e04c9a1b47` carries Intel-OUI hosts already configured for 172.16.44.x and ARPing for a gateway that cannot answer, plus `seat7.local` — a student switch shouting into a void. `enp2s0` carries exactly one device DHCP-requesting **192.168.1.20**, a different subnet. `enx00e04c99a6ba` was **completely silent over 30s despite a 2.5 Gb/s link**. Confirmed no pre-existing loop: no source MAC appears on both `enp1s0` and the sw1 port, so the downstream segments have no second path to the lab. Bridging is the step that joins them.

- 2026-08-18: **The `generic-receive-offload: on (want off)` WARNs in `verify_host` are an ordering artifact, not a capture defect.** `apply_network` runs `udevadm trigger`, which resets every capture NIC to driver defaults; `verify_host` samples the offloads immediately after; but the thing that actually clears them is `netprep`'s `ethtool -K "$i" gro off gso off tso off lro off` (`compose.yaml:92`), which does not run until `start_stack`, several steps later. So the check reliably runs before the fix and reliably warns, on every run, including reruns. Confirm the real state after the stack is up with `ethtool -k <if> | grep generic-receive`. Fixing it means either moving the offload check after `start_stack` or having `verify_host` set them itself — untouched for now because `apply_network` sits on a live link and the ordering there is load-bearing.
- 2026-08-18: **ntop's arm64 package is the Pro build and reports `[LICENSE] Invalid license [Empty license file]` on every start, then falls back to `Edition: Community`.** Verified in a smoke run. Same net behaviour as the amd64 image, but the three WARNING lines look like a fault and are not one. Uncomment `--community` in the compose command block to silence the nag.
- 2026-08-18: **The ntopng package creates `/var/lib/ntopng` (0700, uid 999) but NOT `/var/log/ntopng`**, and `compose.yaml` mounts a named volume onto both. Docker invents the missing mountpoint as root-owned 0755, so it is a silent ownership divergence between the arm64 and amd64 paths rather than a crash. `Dockerfile.arm64` creates it explicitly to match.

- 2026-08-18: **CONFIRMED, int/GW7400: the 5 `lan` ports are DSA switch ports and must NOT be bridged.** The board carries a Microchip KSZ9897STXI driven by the KSZ9477 DSA driver — Gateworks: "This is a Distributed Switch Architecture (DSA) setup. Thus, this is not a 'basic hub' that has everything hardwired together." Mapping is `eth0` = i.MX8MP EQOS + GPY111 (real MAC), `eth1` = i.MX8MP FEC, the CPU uplink to the switch and "never used by itself", `lan1`-`lan5` = KSZ9477 switch ports. Putting `lan1`-`lan5` into `bridge0` makes it a DSA-offloaded bridge: forwarding moves into the switch silicon, `lan2`->`lan3` frames never reach the CPU, and the AF_PACKET tap on `bridge0` cannot see them. Promiscuous mode does not help — the frames are not on the CPU path. ntopng would look healthy and be blind to exactly the intra-LAN traffic an int sensor exists to watch. Consequence: **the earlier open item had it backwards.** The shipped 2-port int netplan was right and must NOT "grow to the board's 5 interface names"; an inline transparent bridge needs exactly two ports, both real independent MACs. The deployed `.env` on gw1 carries the wrong list (`BRIDGE_PORTS=eth0 eth2 lan1 lan2 lan3 lan4 lan5`). Source: https://trac.gateworks.com/wiki/venice/ethernet
- 2026-08-18: **OPEN, blocks the fix above: what is `eth2` on gw1?** The Gateworks wiki documents `eth0`/`eth1`/`lan1`-`lan5` and never mentions `eth2`, but the board reports `eth0` and `eth2` and no `eth1`. Either it is a genuine second MAC (M.2 / mini-PCIe NIC, or the FEC renamed) — in which case `BRIDGE_PORTS=eth0 eth2` is the whole fix — or it IS the DSA conduit, in which case the board has one usable MAC and an inline software bridge needs an add-in NIC, the only alternative being KSZ9477 port mirroring via `tc`, i.e. the SPAN design already ruled out. Settle it with `ip -d link show eth2` (prints `dsa` and names the conduit on a user port) and `ethtool -i eth2`.
- **The shipped int netplan defines 2 ports; the GW7400 has 5.** `10-ntopng-bridge-int.yaml` still carries the `enp1s0`/`enp2s0` example inherited from the ext file. It must grow to the board's 5 real interface names, and `BRIDGE_PORTS` with it. Names unknown at time of writing — open item.
- **Two netplan files defining `bridge0` is not an error netplan reports.** It merges them, last-key-wins by filename order. The legacy `10-outside-firewall-bridge.yaml` sorts *before* `10-ntopng-bridge.yaml`, so an ext host upgraded in place would keep the addressless stanza and look fine — until someone set `POSITION=int` and could not work out why no lease arrived. `retire_legacy_netplan()` renames it to a `.bak`, which netplan does not glob.
- **Under `int`, `netplan apply` cuts the SSH session running the script.** `bridge0` is both the monitored bridge and the management path at that position, so you are connected through the interface being torn down and re-leased. Not true under `ext`, where management is a separate NIC. The script warns specifically for `int`; recovery is to reconnect and rerun, since it is idempotent.
- **`bridge0` under `int` is `optional: true`, so the stack can start before the lease lands.** That is why `WEB_BIND` is a wildcard at that position rather than a pinned address — a pinned one fails to bind on a cold boot. Setting `optional: false` instead would trade that for a two-minute `systemd-networkd-wait-online` stall whenever DHCP is slow or absent.
- **The int bridge's DHCP MAC is inherited from a member port, not from a management NIC.** There isn't one at that position. Read it with `ip -br link show bridge0` before making a reservation; reserving against a physical port's own MAC will not match.
- **STP off + inline on a LAN is a loop waiting to happen.** `stp: false` / `forward-delay: 0` is deliberate — a sensor that joins the spanning tree can have a port blocked, severing the link it is inline on — but it means the bridge forwards blindly. Both ports into the same switch and VLAN is a broadcast storm. Not a risk under `ext`, where one side is the ISP and the other the firewall.
- **`curl http://0.0.0.0:3000/` works on Linux** — the kernel maps a `connect()` to `INADDR_ANY` onto loopback. Verified 2026-08-14 in an alpine container (busybox `httpd` on `0.0.0.0:3000`, curl to both `0.0.0.0` and `127.0.0.1`, both OK). This is why the compose healthcheck can reuse `WEB_BIND` unchanged at both positions. Do not "fix" it to a hardcoded `127.0.0.1`: under `ext`, `WEB_BIND` is the management NIC address and nothing listens on loopback, so the hardcoded form is the one that breaks.
- **A `[[ -n "$x" ]] && log ...` as a function's last statement returns 1 on the empty case** and trips `set -e` in the caller. Hit while writing `verify_bridge_address`; use an `if` block.
- **ntopng needs `CAP_DAC_OVERRIDE` here, and it is not optional.** The image ships `/var/lib/ntopng` as mode `0700` owned by `ntopng:ntop` (uid 999), and a named volume inherits that ownership. `--dont-change-user` keeps the process as uid 0, and root *without* `DAC_OVERRIDE` still cannot enter a `0700` directory it does not own — presenting as `Unable to open lock file /var/lib/ntopng/.lock [Permission denied]` in a restart loop. Verified both ways in isolation 2026-08-14: denied with the capability dropped, writes with it added. Dropping ALL and re-adding only `NET_RAW`/`NET_ADMIN` is what created it.
- **A licensed ntopng feature fails by warning, not by exiting.** `--dump-flows` to an Enterprise-only target leaves the daemon running and apparently healthy while exporting nothing. `--fail-invalid-license` is what converts that into a hard stop; use it if a licence is ever added.
The next four apply to the ClickHouse service that was removed on 2026-08-14. Kept because they cost two debugging rounds to find and would cost them again if a licence is ever bought and the service comes back.

- **Never bind-mount a directory over `/etc/clickhouse-server/config.d` or `users.d`.** Mount the individual files. A directory mount replaces the whole directory and hides what the image ships there, and both directories carry image-provided content that matters. Two separate failures from this, both found 2026-08-14 on the first real `up`:
  - `users.d:ro` → the entrypoint does `cat > users.d/default-user.xml` on every start (whenever `CLICKHOUSE_USER != default`, which is always here), fails with `Read-only file system`, loops, never goes healthy, and compose reports the confusing `dependency failed to start: container ntopng-clickhouse is unhealthy`.
  - `config.d` → hides `docker_related_config.xml`, which is the only thing setting `<listen_host>0.0.0.0</listen_host>`. ClickHouse then listens on the container's loopback only, while the published port forwards to the container's eth0 — so nothing outside can reach it and ntopng's `--dump-flows` could never have connected. Verified with `netstat -lnt` inside the container before and after.
- **ClickHouse's HTTP `/ping` is not proof the native protocol is up.** ntopng uses 9000, not 8123, so the healthcheck runs `clickhouse-client --query 'SELECT 1'`. Measured 2026-08-14: both listeners bind within the same second, so the race is narrow, but the healthcheck should assert the port the dependent actually uses.
- `$$` in a compose command or healthcheck is an escaped literal `$` that the container's shell expands at runtime. Used for `$$CLICKHOUSE_PASSWORD` in the healthcheck so the password stays out of the rendered `docker compose config`.
- **A compose `.env` is not a shell script.** Compose takes the whole rest of the line as the value, so `BRIDGE_PORTS=enp1s0 enp2s0` is legal and means two ports; shell reads it as "run the command `enp2s0` with `BRIDGE_PORTS=enp1s0` in its environment". Hit 2026-08-14 as `./.env: line 19: enp2s0: command not found`, which killed the script under `set -e`. `host-setup.sh` now parses `.env` line by line instead of sourcing it — which also stops a setup script running under sudo from executing whatever a config file happens to contain. Verified the parser against unquoted-with-spaces, double- and single-quoted, inline comments, `export` prefixes, indentation, and a password containing `$`, `!` and `#`. `.env.example` quotes the value as well; compose strips the quotes and reads both forms identically (verified by running the netprep loop both ways).
- **Compose treats an unset variable as a blank string and only prints a `WARN`.** Verified 2026-08-14: `--http-port=${WEB_BIND}:${WEB_PORT}` with no `.env` renders as `--http-port=:`, which ntopng binds on every interface. On a box outside the firewall running default `admin`/`admin`, that publishes the admin UI. `:-` defaults on any variable whose blank value is dangerous, not just the ones that look required.
- **The netplan-generated `.network` unit name is not guaranteed.** A drop-in directory that does not match it exactly is ignored without any error, `bridge0` never goes promiscuous, and ntopng reports near-zero flows on a bridge that is plainly passing traffic. The script globs `/run/systemd/network/*${MON_IF}.network` and then proves the merge with `systemd-analyze cat-config | grep '^Promiscuous=yes'` rather than trusting either.
- **`br_netfilter` must be loaded before `sysctl --system`.** The `net.bridge.*` keys do not exist until then, so the settings are silently dropped and the bridge stops forwarding the moment Docker loads the module itself.
- **The host has no default route by design.** Addressless bridge, gateway-less management NIC. `docker compose pull` cannot work; images must be `docker save`/`docker load`ed in. The script checks every image compose reports before doing anything.
- `ethtool -G` is unsupported on virtio and some Intel parts. Read `ethtool -g` first, clamp the request to the pre-set maximum, and warn rather than fail.
- `netplan apply` on this host interrupts the live ISP link for everything behind the firewall. The script asks first (`ask_confirm`, defaults Y).
- The `host/*.conf` glob that installs sysctls would also sweep up any other `.conf` in `host/`. `ntopng-tap.service` is safe only because of its extension.
- The qol theme block's `_term_cols` reads `stty size </dev/tty`, which prints `/dev/tty: Device not configured` to stderr when there is no controlling terminal (piped output, CI). Cosmetic, harmless, and not ours to patch here — the block is byte-synced against `~/projects/qol/linux/base_functions.sh` and `tests/test-theme-sync.sh` is exact on purpose. Does not affect the boot unit, which runs `docker compose up -d` rather than this script.

## Ruled out

- 2026-08-18: **qemu binfmt emulation (`platform: linux/amd64` + `qemu-user-static`) to run the upstream image on arm64.** It would start, but emulating a packet-capture hot path on four Cortex-A53s drops frames. Emulation is the wrong tool for the one job this box has.
- 2026-08-18: **Third-party arm64 ntopng images on Docker Hub** (`phantomski/ntopng`, `gsdukbh/ntopng`, `edgd1er/ntopng`). Unverified provenance and stale builds. Not acceptable for a stack that ships as a teaching artifact.
- 2026-08-18: **Native (non-container) ntopng install on the board from ntop's apt repo.** `packages.ntop.org/apt-stable/24.04/` publishes `all/` and `x64/` only — no arm64 for Ubuntu noble. The arm64 builds live in the RaspberryPI Debian repos, which do not match noble.

- A separate `ntopng-int` package alongside `ntopng-ext`: the delta is four knobs against ~1100 lines of shared script and a byte-identical `compose.yaml`. Two copies of the script would have drifted within a week.
- Generating the netplan from `.env` in `host-setup.sh`: would have fixed the `BRIDGE_PORTS`-must-match-the-yaml duplication, but the user wants the netplan to stay an editable file in `etc/netplan/`.
- A static address on the int bridge: DHCP was the explicit call. The cost is that `WEB_BIND` cannot be pinned; the mitigation is mDNS or a reservation.
- Wildcard `WEB_BIND` as a per-run prompt with default N, or a one-time `.env` acknowledgment flag: the first punishes a script whose whole design is "rerun it freely", the second is more machinery than the warning is worth. Warn loudly, prompt with default Y.
- SPAN / mirror-port mode as `POSITION=span`: see the decision above — it is a different design, not another value.
- Sourcing `base_functions.sh` with the GitHub download fallback: needs a default route, which this host does not have.
- Making `--dump-flows` conditional through an env var: compose cannot omit a command argument, and an empty array element is passed to ntopng as an empty argv.
- Keeping ClickHouse in any form without an Enterprise licence: the export is licence-gated, so every arrangement of it reserves memory for output that never arrives.

## Constraints

- 2026-08-18: **The `int` sensor host is a Gateworks GW7400 — arm64 (i.MX8M Plus, 4x Cortex-A53), 3.8 GiB usable RAM, 4 cores, no swap.** This is the 4 GB DRAM variant; Gateworks also ships a 1 GB one, which would be below ntop's own floor. Verified on the box with `nproc` / `free -h`.
- 2026-08-18: **`ntop/ntopng:latest` is amd64-only** — `ntop/ntopng` and `ntop/ntopng.dev` each publish exactly one tag, `latest`, single-arch amd64. There is no official arm64 ntopng image on Docker Hub. Official arm64 *packages* do exist, in `packages.ntop.org/RaspberryPI/{bookworm,trixie}_pi/arm64/ntopng/`, currently 6.7. `redis:7-alpine` and `nicolaka/netshoot` are multi-arch, so only the ntopng service breaks on arm64.
- 2026-08-18: **The board sits in ntop's *Medium* sizing tier (4 GB+, 4 cores+; 100 Mbps-1 Gbps, thousands of hosts, hundreds of thousands of flows), not *Large*.** The shipped `.env.example` is sized for Large on a 32 GB host. `MAX_FLOWS` / `MAX_HOSTS` are what actually consume the RAM, so they bind first. Source: https://www.ntop.org/guides/ntopng/performances/hardware_sizing.html
- 2026-08-18: **nDPI throughput on Cortex-A53 will land below ntop's Medium tier figure**, which is not benchmarked against in-order low-power cores. Fine for a LAN whose sustained load is a fraction of gigabit; not a line-rate 1 Gbps DPI box.

- Ubuntu Server 24.04, systemd 249+, 32 GB. Two supported positions: `ext` between the ISP and the firewall's outside edge, `int` inline on a LAN link inside it.
- `bridge0` carries production traffic at either position; every change to it is an outage window.
- `LOCAL_NETS` is position-dependent and there is no safe default. Under `ext` it must be the WAN prefix, never the inside LAN — post-NAT, no RFC1918 address appears on that wire. Under `int` it must be the internal subnets, all of them, including VLANs trunked across the link. The script warns on either mismatch but cannot refuse, since both can be legitimate on an unusual link.
- `compose.yaml` must stay identical at both positions. The moment it needs a `POSITION` branch, the case for one package is weaker than the case for two.
- Scripts follow the qol house style (`~/projects/qol/script-design.md`); filenames stay lowercase-hyphen.
